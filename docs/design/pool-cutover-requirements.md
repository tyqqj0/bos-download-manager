## 0. 为什么现在做（触发事件）

2026-08-08 12:53 实测：7 个分片死了 3 个（w1、w5、w7）。死因不是网络，是
`dlm/temporal/activities.py:407` 的全有全无判定：

```
Batch incomplete: 1/500 files failed (downloaded=499, uploaded=499)
```

一个文件失败 ⇒ 整批失败 ⇒ 三批耗尽 `maximum_attempts=3` ⇒ 分片判死 ⇒
协调器不重试（`dlm/temporal/workflows.py:847`）⇒ 整个任务落 `failed`。
失败任务永不自动重派，所以两个任务本轮都到不了 100%。

Pool 模式针对性地解决三点：批次爆炸半径从 1/4 数据集降到 ≤32 GiB、
有失败批次重派轮（`workflows.py:1100`）、空闲 worker 自动接单（不会出现
w1/w7 空转 8.5 小时而任务还缺数据）。

**实测基线（切换前，用于验收对比）**

| 任务 | id | BOS 实测 | 声明总量 | 剩余 | 对象数 |
|---|---|---|---|---|---|
| RealOmin | `t-20260806-319c55` | 15,966.0 GB | 25,765.0 GB | 9,799 GB | 239,663 |
| molmobot-data | `t-20260805-460d45` | 6,222.9 GB | 8,446.9 GB | 2,224 GB | 2,790 |

BOS 前缀：`auwomo-data/manipulation/RealOmin/`、`auwomo-data/other/molmobot-data/`。
**这两个数字是数据安全的锚**：切换后任何时刻 BOS 字节数只允许增加，
一旦下降就是事故，立即停止并回滚。

## 1. 需求（R）

### R1 —— 新 BOS Key 在全部 17 台生效

轮换后的 Key 已写入 17 台 `.env`（2026-08-07），但 worker 进程仍持有旧 Key：
env 在 exec 时读取，`dlm/core/config.py::load_config` 用的 `load_dotenv` 没有
`override`，改 `.env` 对运行中的进程无效。旧 Key 是 **PUT 活、LIST 死**
（`SignatureDoesNotMatch`），所以上传一直正常而所有依赖 LIST 的功能静默失效 ——
包括续传过滤器 `filter_filelist_against_bos`。

**这不是卫生问题，是前置条件**：resume / reshard / 重派都要跑 BOS LIST，
旧 Key 下必然失败。所以重启是恢复这两个任务的必要步骤。

验收：见 A1。

### R2 —— Pool 模式代码部署到 17 台并生效，全局默认为 pool

用户明确批准："全局默认都改成 pool 池模式"。含义拆解为三类行必须都落在 pool 上：

- a) 全新建的任务（两条入口：Web 表单、`/api/queue/add`）
- b) 已存在的 `pending` 行
- c) 被重派的 `failed` / `paused` 行

> **修正（2026-08-08，实测）**：b) 原先写作"`dispatch_mode IS NULL` 的 pending 行"，
> 这个前提**不成立**。SQLite 的 `ALTER TABLE tasks ADD COLUMN dispatch_mode TEXT
> DEFAULT 'sharded'`（`snapshot.py:132`）在迁移那一刻就把**所有存量行**物理写成字面量
> `'sharded'`，从不留 NULL（本地 sqlite 实测：两行存量行迁移后均读出 `'sharded'`，
> `dispatch_mode IS NULL` 命中 0 行）。因此 Python 侧"None 则取
> `DEFAULT_DISPATCH_MODE`"的逻辑对存量行**永不触发** ——
> 翻转环境变量/代码默认值只影响新建行。b) 和 c) 必须靠显式回填或逐个 reshard 落地。

三类都必须走 pool，缺一类就不算"全局默认"。

验收：见 A2、A3。

### R3 —— 数据安全三条底线

用户原话确认的三件事，逐条对应一个可验证的机制：

| 底线 | 机制 | 状态 |
|---|---|---|
| **不重下已有数据** | 两层过滤：协调器级 `filter_filelist_against_bos` + 每批次 `_head_skip_filter`（`activities.py:1207`） | 已有能力，需验证 |
| **不弄坏已下好的数据** | pool 路径只 PUT，无任何 BOS delete；所有 `rmtree` 只针对本地 staging | 已有能力，需**证明** |
| **不落下数据** | ⚠️ **现有代码不满足** —— 见 R4 | **本次要新增** |

前置条件：重派**必须复用原 `name` + `category`**，否则 `bos_target()` 算出的前缀变了，
续传过滤器一个文件都匹配不上，等于从零重下 22.2 TB。

验收：见 A4、A5、A6。

### R4 —— 缺件不再静默：批次容忍 + 缺件记账

这是本次唯一的**新增功能**，也是"不落下数据"从口头保证变成真保证的关键。

现状：`run_pool_batch` 在 `stats.failed_files > 0` 时抛异常（`activities.py:1274`），
和 sharded 一样是全有全无。差别只是爆炸半径。但源端永久坏文件（例如 ModelScope
把 RoboDojo 的 depth 文件当 0 字节发）会让同一批次两轮都失败，任务照样落 `failed`
且缺那一批 —— 而**哪些文件缺了，只存在于某台 worker 的一行日志里**，
库里没有任何记录，仪表盘看不见，搬运门槛也无从判断。

需求：
- 批次允许少量永久失败文件而不整批判死（阈值可配，默认值在方案里定）
- 每个失败文件必须**持久化记录**（哪个任务、哪个批次、哪个文件路径、失败原因），
  可查询、可在仪表盘或 API 暴露
- 超过阈值仍然失败整批（不能把阈值做成"永远不失败"）
- 任务收尾时的状态语义：见下方修订

> **修订（2026-08-08，用户决定）**
>
> 原文写的是"只要存在缺件记录就不允许报 `done`"。用户明确改为：
> **少量缺件属正常，任务照报 `done`，照走搬运。**
> 原话："缺文件好像是挺正常的事情……他说可以搬就搬呗。"
>
> 这个改动在设计上更强而不是更弱：**诚实性由"持久化记录 + 告警"承担，不由状态承担。**
> 状态报 `failed` 只会让人不敢信自动化（而且 `failed` 任务永不自动重派、也不触发搬运，
> 等于把一个 99.999% 完成的 22 TB 数据集卡死等人工）。真正的"不落下数据"是
> **知道缺了哪些**，而不是拒绝说完成。
>
> 修订后的收尾语义：
>
> | 复核后剩余缺件 | 上报 | 告警 |
> |---|---|---|
> | 0 | `done` | 无 |
> | 0 < N ≤ 上限 | **`done`** | **WARNING（必发，含缺件数与可查接口）** |
> | N > 上限 | `failed`，错误信息含缺件数 | CRITICAL |
>
> **上限必须存在**，否则阈值退化成"永远不失败"（这一条原文要求未被修订）：
> 单批次容忍 5 个，而一个任务可有 1500 个批次 —— 累计 7500 个缺件不是"几个"。
> 上限取 `max(绝对下限, 本轮总文件数 × 比例)`，默认 `max(10, 0.5%)`，两个值均可配。
> 绝对下限的作用是别让小任务被比例误伤。
>
> **绝不静默**：无论落在哪一档，缺件一律入库、一律可查；第二档必发 WARNING。
> 这是"不落下数据"从口头保证变成真保证的那个机制，未被修订。

验收：见 A6、A7。

### R5 —— 旧东西清理干净

两个层面，都要在方案里列清单，且**区分"现在能删"和"必须留"**：

- **代码层**：切到 pool 后 sharded 路径的哪些部分变成死代码。
  硬约束：凡是 Temporal replay 需要的（workflow 类注册、
  `tests/fixtures/histories/` 的 replay 测试）**一律保留**，
  否则历史 workflow 重放会崩。默认保留，只删证明安全的。
- **运行时层**：死分片和已终止任务留下的 staging 目录、陈旧的 `/root/.env`、
  重派前必须处理的旧 shard 行。仍在运行的分片的 staging **绝对不能碰**。

验收：见 A8。

### R6 —— 数据能正常下起来、全都是对的、不卡住

"正常"必须量化，不能靠"看起来在跑"：

- 两个任务都在 pool 模式下运行，batch 行在流转（不是全部 pending 或全部 running 不动）
- 窗口被填满（在飞批次数达到设计值，不是只有 1 个）
- 每台参与的 worker 都在实际下载（不是少数几台在扛）
- BOS 字节数单调增长，且增速与聚合速度一致（防止"报了速度但没落盘"）
- 无批次卡在 running 超过合理时长

验收：见 A9、A10。

### R7 —— 自动分派（auto_dispatch）在 pool 下正确工作

`reconciler.auto_dispatch_pending()` 每 30s 跑一次，其"协调器仍在列表阶段则跳过"
的守卫是按 sharded 的形状写的（downloading 任务 + 零 shard 行 + 新鲜 `claimed_at`）。
必须确认这个守卫在 `PoolDownloadWorkflow` 下依然成立，
且不会出现重复派发或永久跳过。

验收：见 A11。

### R8 —— 监控一段时间并如实汇报

部署后不是"起起来就完事"。需要一段观测期，用分片/批次级真相验证，
而不是只看仪表盘聚合数字（聚合数字被 `downloaded_gb` 只算本轮的语义误导过一次）。

验收：见 A12。

### R9 —— 自动搬运（#83），条件性

用户原话："如果说不好搞，先太多任务的话先不搞。"

判定规则（方案阶段决定，不留悬念）：
- 若 #83 的实现能落在**本次改动之外的独立提交**、且不改动 pool 关键路径 ⇒ 纳入，但排在 pool 验收通过之后
- 若它需要改动 pool 关键路径、或会让本次改动量翻倍 ⇒ **明确推迟**，写清推迟的边界和下次的入口

无论纳入还是推迟，都必须在方案里给出结论和理由，不能含糊。
设计文档已存在：`docs/design/auto-transfer-trigger.md`（其中已确认 pool 与该功能的
两个交汇点是模式无关的，且顺序是先 pool 后搬运）。

验收：见 A13。

## 3. 硬约束（继承，全程有效）

1. **绝不删除 BOS 上已下载的数据**，未经用户明确批准。staging 清理只针对 done/skipped/failed 任务。
2. **只走系统层**：一切通过 API / Temporal。框架做不到就升级框架，绝不手工起下载进程。
3. **不许混版本**：批量操作前必须用部署脚本的 md5 manifest 确认 17/17 一致。SQLite 是唯一状态源。
4. **worker 重启一律走 `deploy-workers.sh`**，绝不 `ssh setsid`（随会话死）。用 `ps` 而非 `pgrep -f` 核实。
5. **重派必须复用原 `name` + `category`**（决定 BOS 前缀）。
6. `workflows.py` 必须保持确定性；改动已跑起来的 workflow 定义会让 replay 崩。
7. **绝不打印凭证值**（BAIDU_AK/SK、HF_TOKEN、MODELSCOPE_API_TOKEN、DCLOUD）。可报长度或 sha256 前缀。
8. **不 tail 原始 worker 日志**（单行含 KB 级 CDN URL）。一律 `grep -c` / 时间窗 awk / `cut`。

## 4. 验收标准（A）

每条给出**判定方式**。"通过"= 判定方式跑出预期结果并留下证据。

### A1 —— 新 Key 在 17 台全部生效

- 17/17 台 worker 进程的启动时间晚于本次部署时间（`ps -eo etimes,args`，不用 `pgrep -f`）
- 17/17 台用**进程实际持有的**凭证做的 BOS 探测：LIST、HEAD、`does_bucket_exist` **三项分别** OK
  （旧 Key 的特征是 PUT/HEAD 活而 LIST 死，所以必须分项探，一次调用不算）
- 17 台的 AK sha256 前缀彼此一致

### A2 —— 代码 17/17 一致

- 部署脚本输出的 md5 版本清单 17/17 全部匹配
- S1 侧记录本次部署的提交（`git rev-parse --short HEAD`），并与 md5 清单一起留档
- 部署前已确认无主机存在未提交的本地修改（否则会被 rsync 静默覆盖）

> **修订（2026-08-08）**：原文第二条写"17/17 台 `git rev-parse --short HEAD` 相同"，
> **不可满足**。`deploy-workers.sh` 的 rsync 带 `--exclude '.git'`（脚本 140 行），
> worker 上根本没有 git 仓库（或只剩某次旧 clone 的残留），在 worker 上跑
> `git rev-parse` 要么报错要么给出一个与实际部署代码无关的旧提交 ——
> 拿它当验收会得到一个看起来通过、实际什么都没验的门。
> **md5 清单才是唯一可信的一致性证据**：它按 rsync 能搬的文件逐个哈希，
> `--delete` 成功后两侧目录树完全相同。提交号只在 S1 一侧有意义，用于留档回溯。

### A3 —— 全局默认确实是 pool（三类行都验）

- a) 新建任务：经 Web 表单和 `/api/queue/add` 各建一个测试任务，库里 `dispatch_mode` 读出为 `pool`
- b) 存量 pending 行：迁移后逐行确认 `dispatch_mode='pool'`（回填生效），且被派发时走 pool
  （观测到 `PoolDownloadWorkflow` 而非 `ShardedDownloadWorkflow`）
- c) 被重派的 failed/paused 行：同上
- 回填**不得触碰 `downloading` 行**（回填前后各查一次 `downloading` 行的
  `dispatch_mode`，必须不变）
- 三个 worker 队列注册正确：HF 主机轮询 `download-workers` / `download-wN` / `pool-hf`，
  bj 主机轮询 `download-bjN` / `download-ms-workers` / `pool-ms`

### A4 —— 不重下已有数据（可量化）

- 重派后，两个任务的协调器上报的 `resume_skipped` 字节数量级与 BOS 实测已有字节一致
  （RealOmin ≈ 15,966 GB，molmobot ≈ 6,223 GB）
- 重派后 24 小时内 BOS 对象总数的增量 **远小于**"从零重下"会产生的增量
  （若出现接近 239,663 的对象增量，说明前缀错了，立即停）
- 抽查：任取若干已存在的 BOS key，确认重派后其 `last_modified` **未被刷新**

### A5 —— 不弄坏已下好的数据

- pool 全路径静态审计：除 `put_object*` 外无任何 BOS 变更调用（无 `delete_object(s)`、无生命周期操作）；所有 `rmtree`/`unlink` 的目标目录逐一确认为本地 staging
- 运行期间两个前缀的 BOS 字节数**单调不减**（观测期内多次采样，任何一次下降即事故）
- 对象数同样单调不减

### A6 —— 不落下数据（结构性保证，不是运气）

- 存在缺件的持久化记录机制，且能通过查询/API 列出"任务 X 缺哪些文件"
- 该记录**不得**依赖 `events` 表 —— 它是 24 小时滚动缓冲（`servers.py:313-314` 每次收事件都
  `DELETE FROM events WHERE timestamp < now-86400`），不是档案
- 构造一个必然失败的文件（例如源端 0 字节）验证：批次不整批判死、缺件被记录、阈值超限时仍然失败
- 任务收尾时（按 R4 修订后的语义）：缺件数 ≤ 上限 ⇒ 报 `done` **且必发 WARNING 告警**；
  超上限 ⇒ 报 `failed`。两档都必须能通过接口列出缺了哪些文件。
  **"报了 done 但没有告警、也查不到缺件"是本条唯一的失败形态。**

### A7 —— 容忍阈值行为正确

- 低于阈值：批次通过，缺件入账，任务可继续
- 高于阈值：批次失败，走重派轮，两轮都失败则任务 `failed` 且错误信息含缺件数
- 阈值可配置，默认值在方案中给出并有理由

### A8 —— 旧东西清理干净且没删错

- 代码层：死代码清单已给出 keep/delete 决策与理由；replay 测试在清理后依然全绿
- 运行时层：清理的 staging 目录清单与"仍在运行的分片"清单**无交集**（清理前后各记录一次）
- 全量测试通过（**部署前基线 627 passed**，2026-08-08 于 `17a7ff6` 实测）。
  演进：需求定稿当天 453 → T1–T7 pool 改动完成 599 → 评审第 1 轮修复 627
- replay 测试（`tests/test_workflow_replay.py`、`tests/test_pool_workflow_replay.py`，
  **当前 41 passed**）通过 —— 这两个文件回放 `tests/fixtures/histories/` 里录下的 7 份
  真实历史，是 R5 "清理不许破坏 replay" 的唯一证据

> **修订（2026-08-08）**：原文写的 "453 passed" / "27 passed" 是需求文档定稿当天的数字，
> 到代码完成时已过时。**过时的基线比没有基线更糟**：验收时跑出 627 会被读成"多了 174 条，
> 有人塞了东西"，或者反过来，真的掉了测试也看不出来。数字随每次提交变，
> 所以这里同时记下取数的提交号；验收时以"跑一次 == 记录值，且无 failed/error"为准，
> 而不是记死某个数。

### A9 —— 两个任务在 pool 下真的在下

- 两个任务 `dispatch_mode='pool'`、状态 `downloading`
- batch 行在流转：观测两次，`done` 批次数增加
- 在飞批次数达到窗口设计值
- 参与下载的 worker 数量符合预期（不是少数几台在扛）

### A10 —— 不卡住（用 BOS 真相验证，不信聚合数字）

- 两个 BOS 前缀的最新对象 `last_modified` 距当前 < 10 分钟
  （注意：BOS 返回 UTC，必须用 `calendar.timegm` 解析；`time.mktime` 会按本地时区多算 8 小时，已踩过）
- BOS 字节增速与仪表盘聚合下载速度同量级（差一个数量级说明"报了速度没落盘"）
- 无批次卡在 `running` 且 `updated_at` 超过合理阈值

### A12 —— 观测期通过

- 部署后持续观测，期间：无新增死批次累积到任务失败、BOS 单调增长、
  **无"非预期"告警**（见下方修订）
- **pool 任务不会自愈,所以观测期是硬要求而非可选**：`reconciler.reconcile()` 的孤儿重派
  分支对 pool 任务**显式 `continue` 跳过**（`reconciler.py:183` 附近，"decision C"）——
  理由是第二个 `PoolDownloadWorkflow` 会重跑 list→filter→chunk 并撞上批次不匹配从而卡死
  任务。sharded 任务卡住 30 分钟后会自动重派，**pool 任务不会**，只会产出
  `pool_orphaned` / `pool_starved` 告警等人处理。
  所以验收必须包含：确认这两个告警确实会出现在 `/api/dashboard`，并在观测期内实际盯它们。
- 观测结论如实汇报：包括"哪些指标我没能验证"

> **修订（2026-08-08）**：第一条原文写"无告警"，与 R4 修订后的语义**直接冲突** ——
> R4 规定缺件数在 `0 < N ≤ 上限` 时任务照报 `done` 且**必发 WARNING**，A6 更把
> "报了 done 但没有告警"列为唯一的失败形态。若 A12 按字面执行，
> 一个正确工作的系统（有几个源端坏文件 + 一条如实的 WARNING）会被判为观测期不通过，
> 而把 WARNING 消掉才能"通过"—— 正好奖励了 R4 要消灭的静默。
>
> 修订为按告警类型判定：
>
> | 告警 | 观测期判定 |
> |---|---|
> | 缺件 WARNING（`0 < N ≤ 上限`） | **预期**，出现即说明记账链路通了；记录缺件数与任务，不算不通过 |
> | `pool_orphaned` / `pool_starved` | **非预期**，出现即人工介入（pool 任务不自愈，见上） |
> | 缺件 CRITICAL（`N > 上限`）、任务 `failed` | **非预期**，停下查因 |
> | BOS 字节数下降 | 事故，走第 5 节回滚 |

## 5. 回滚

前提：**BOS 上的数据在任何回滚路径下都不受影响**（只 PUT，从不 delete），
所以回滚的代价只是时间，不是数据。

| 触发 | 动作 |
|---|---|
| BOS 字节数下降 | 立即停止全部派发，暂停两个任务，查清原因后再动。最高优先级事故。 |
| 部署后 worker 起不来 / md5 不齐 | 回滚到部署前提交并重新部署，两个任务保持 paused |
| pool 批次大面积失败 | 把两个任务的 `dispatch_mode` 改回 `sharded` 重派（sharded 路径保留，见 R5） |
| 全局默认翻转导致新任务异常 | 单独回退默认值，不必回退整个部署 |
